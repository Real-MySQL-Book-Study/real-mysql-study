# JDBC와 MySQL의 소통 방식: Buffering vs Streaming

JDBC(Java Application)와 MySQL(Database)이 데이터를 주고받을 때, **"데이터를 드라이버가 언제, 얼마나 쥐고 있다가 애플리케이션에 넘겨주는가"**가 핵심 차이입니다.

---

### 1. 기본 개념 정의

* **Buffering (버퍼링):** "일단 내가 다 받아서 창고에 쌓아둘게. 다 도착하면 그때 가져가."
* **Streaming (스트리밍):** "도착하는 대로 창고에 넣지 않고 바로 넘겨줄게."

---

### 2. JDBC <-> MySQL 소통 상세

MySQL JDBC 드라이버(Connector/J)는 기본적으로 **Fetch Size 설정을 무시**하며, 아래 두 가지 모드로만 동작합니다.

#### (1) Default: 버퍼링 (Buffering) - "전체 적재 후 전달"
MySQL 드라이버의 기본 설정입니다. 아무런 설정을 하지 않으면 이 방식으로 동작합니다.

* **소통 흐름:**
    1.  **App:** `executeQuery("SELECT ...")` 요청.
    2.  **MySQL Server:** 결과 데이터(Packet)를 네트워크를 통해 계속 보냄.
    3.  **JDBC Driver:** 서버가 보내는 모든 패킷을 받아서 **JVM 메모리(Heap)에 전부 저장**함. (이때 App은 대기)
    4.  **MySQL Server:** "전송 끝" 신호.
    5.  **JDBC Driver:** 이제야 App에게 "준비됨" 신호를 줌.
    6.  **App:** `rs.next()`를 호출하면 메모리에 있는 데이터를 빠르게 꺼내 씀.

* **Why (이 방식이 기본인 이유):**
    * **DB 서버 부하 감소:** 데이터를 빨리 털어내고 연결을 끊거나 다른 요청을 받을 수 있어 DB 입장에서 효율적입니다.
    * **조회 속도:** 이미 메모리에 다 와있기 때문에, 앱 내부에서 데이터를 순회하는 속도가 매우 빠릅니다.

* **문제점:** 데이터가 100만 건, 1000만 건이 넘어가면 드라이버가 힙 메모리를 다 써버려서 **OOM(Out Of Memory)**이 발생합니다.

#### (2) Option: 스트리밍 (Streaming) - "받는 즉시 전달"
대용량 데이터를 처리해야 할 때 사용하는 방식입니다.

* **설정 방법:**
    ```java
    stmt.setFetchSize(Integer.MIN_VALUE); // 필수 설정
    ```
* **소통 흐름:**
    1.  **App:** `executeQuery("SELECT ...")` 요청.
    2.  **MySQL Server:** 첫 번째 데이터 패킷 전송.
    3.  **JDBC Driver:** 데이터를 메모리에 쌓지 않고, **네트워크 소켓에서 읽자마자 바로 App으로 전달**.
    4.  **App:** `rs.next()` 한 건 처리.
    5.  **MySQL Server:** (App이 처리를 끝낼 때까지 대기했다가) 다음 패킷 전송.

* **Why (언제 쓰는가):**
    * **메모리 절약:** 아주 적은 메모리로 수천만 건의 데이터를 처리할 수 있습니다.

* **주의점:**
    * **커넥션 점유:** 데이터를 다 읽을 때까지 해당 DB 커넥션은 다른 쿼리를 실행할 수 없습니다.
    * **네트워크 비용:** App의 처리가 느리면 DB와의 통신 시간이 길어집니다.

---

### 3. 한눈에 보는 비교

| 구분 | 버퍼링 (Default) | 스트리밍 (Option) |
| :--- | :--- | :--- |
| **데이터 위치** | **JVM 메모리**에 전체 저장 | **네트워크 소켓**에서 실시간 수신 |
| **메모리 사용량** | 데이터 양에 비례 (높음) | 매우 낮음 (일정함) |
| **전송 시점** | 전체 데이터 수신 완료 후 | 첫 번째 데이터 수신 즉시 |
| **설정** | 별도 설정 없음 | `setFetchSize(Integer.MIN_VALUE)` |
| **주요 용도** | 일반적인 웹 페이지 조회 (게시판 등) | 배치(Batch) 작업, 대용량 엑셀 다운로드 |


### 추가 

보통 불확실성 제어를 위해서(속도 불일치 문제 해결 등) 스트리밍-버퍼링 구조는 많이 쓰인다!
서버에서는 실시간으로 데이터를 계속 보내지만, 클라이언트에서는 네트워크 불안정을 대비해서 일정량을 미리 받아서 버퍼에 쌓아두는 형태(유튜브의 회색 게이지)
